# Host protection

Native Kali uses the current nonroot Linux user and retains the same logging, scope checks, and root approval flow. It is not a host filesystem sandbox. Workspaces persist under `~/.local/share/harp/runs/`; finishing a session stops HARP-managed Whippet processes but does not delete Kali files or shut down the VM. Imported Linux API keys are unencrypted owner-only files, unlike Windows DPAPI storage. Use a dedicated lab VM when host separation is needed.

In Docker mode, each session gets a disposable Kali container. It runs as UID 10001 by default, with a read only root filesystem, small writable `/tmp` and `/workspace` memory filesystems, no Windows drive mount, no Docker socket, no published ports, no privileged mode, a PID limit, a CPU limit, and a 512 MiB memory limit by default. All Linux capabilities are dropped except `NET_RAW`; Nmap receives that capability through its file capability for SYN scans. Other root commands still require separate approval. Commands and output are time and size bounded. When the session ends, HARP removes the container and its temporary files.

The proxy model cannot call Docker or the Windows shell. It can request a root command; HARP stops the delegation and exposes that exact command for human approval. The command center has an approval button for these requests. The `terminal_root` MCP tool is also configured in [`.codex/config.toml`](../.codex/config.toml) with `approval_mode = "approve"`; while the command center is open, it requires an additional approval there. A root approval increments `root_approvals`; it does **not** mark human tactical intervention. A manual Kali command entered in the web app does mark tactical intervention. The CLI intentionally refuses `root-exec` so the normal workflow cannot silently bypass the approval path.

Before a delegated command executes, HARP checks shell syntax inside Kali and applies plan-scope checks for the primary target and any SMB share named in the oracle objective. A private pivot IP found in successful terminal evidence is allowed when the current oracle objective names that exact IP. The optional `authorized_scope` config list can predeclare additional IPv4 addresses or bounded CIDRs. A new public IP, or a private IP without both evidence and a current objective, triggers human review. In Strict mode HARP also flags interactive `smbclient mget` without `prompt off`, a known filename-quoting mistake, named accounts in an explicit null-only task, and SMB passwords without terminal evidence. Essential mode leaves those tactical choices to the model. Any command-check issue pauses the proxy and opens an exact-command review in the command center; acceptance runs that command and denial returns feedback to the proxy. Review waiting time is recorded separately and does not consume a proxy step or count toward active time to success. A null-auth access denial returns control to the oracle for replanning. These checks do not prove that every action advances the plan, so the oracle still reviews terminal evidence after each bounded delegation. Identical duplicate JSON actions are accepted; after a malformed reply HARP retries at lower temperature and, for Unsloth, with thinking disabled.

The WSL runtime uses your existing distribution, whose Windows mounts and home files are accessible to Kali commands. It does not provide the Docker container isolation or resource limits. HARP uses a per-session directory under `/home/<user>/.local/share/harp/runs/`, but that directory is not a security boundary. Use WSL mode only for trusted proxy models and authorized targets. HARP leaves the WSL workspace on disk after a session; remove it yourself after preserving evidence.

Containers are a practical boundary, not a guarantee against a container escape or against reaching Windows network services when using an outbound bridge. Keep Docker Desktop and Windows updated. For stronger host separation, use Docker Desktop Enhanced Container Isolation or a dedicated VM. Do not add host bind mounts, `--privileged`, Docker socket mounts, or host networking to the worker. The provided lab uses an internal bridge with an isolated gateway. The VPN mode uses a separate outbound bridge and therefore relies on the Windows VPN and your host firewall for network routing and scope.
